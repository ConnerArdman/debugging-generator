## 1. Scope and threat model

### 1.1 Assets

Debug Generator touches three things a developer cares about. It **writes to their source tree**: a small number of named functions are temporarily wrapped so their execution can be timed. It **reads their application's runtime data**: interactions, React renders, requests, server spans and database queries from the app being debugged, plus the project's source code for indexing. And it **may send data off the machine**: when a model provider is configured, the provider credential authenticates requests that carry redacted, bounded excerpts and aggregates. This document covers all three, together with the credentials and local state the product itself creates.

### 1.2 Trust assumptions

- Every component runs as the developer's own OS user on their own machine: the VS Code extension, the local service (`apps/local-service`), the Chrome extension, and the Node preload inside the developer's dev server.
- The service binds to loopback (`DEBUGGEN_HOST`, `127.0.0.1` by default). **Loopback is not an authorization boundary.** It keeps other machines out, but any other process on the machine and any web page the developer visits can open a connection to a loopback port. That is why every client authenticates with a role-bound credential and every web origin is refused ([section 7](#7-local-service-access-boundary)).
- Everything a page produces is untrusted input. The page under debug shares a JavaScript realm with the telemetry agent, so the service validates, bounds and redacts every event it receives, and treats a source location arriving from the panel as hostile until it is proven to lie inside the project ([section 6.5](#65-source-open-containment)).
- The model provider is a third party. What it receives is bounded and redacted ([section 4](#4-what-may-leave-the-machine-and-when)); nothing it returns is executed ([section 5](#5-model-provider-boundary)).

### 1.3 Adversaries considered

| Adversary                                       | What it can attempt                                                               | Primary control                                                                                                                                                                                               |
| ----------------------------------------------- | --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A web page open in the developer's browser      | Reach the loopback service with `fetch` or a WebSocket; trigger a `vscode://` URI | Origin policy, no CORS grant and bearer credentials ([section 7](#7-local-service-access-boundary)); independent URI-handler validation and a modal confirmation ([section 6.5](#65-source-open-containment)) |
| A script on the local app origin being debugged | Forge frames between the page agent and the bridge; feed misleading telemetry     | A private node the agent hands the bridge at `document_start`, and provenance pinning ([section 9.1](#91-chrome-extension)); ingest validation, bounds, redaction and source re-verification                  |
| A local process that cannot read your files     | Call the service; brute-force pairing                                             | Bearer credentials on every route; single-use pairing codes, compared exactly, with a single service-wide lockout                                                                                             |
| Another OS user on the machine                  | Read session data, backups or credentials                                         | `0700` directories and `0600` files, created without following symlinks ([section 8](#8-session-data-at-rest))                                                                                                |
| Model output                                    | Smuggle instructions, code or markup into the product                             | Schema validation, deterministic normalisation, no execution, catalogued components only ([section 5](#5-model-provider-boundary))                                                                            |

### 1.4 Non-goals

These guarantees are **not** offered and should not be inferred:

- no multi-user, team or shared-service model — one developer, one machine;
- no enterprise authentication, single sign-on or central policy;
- no hosted component — nothing of this product runs off the machine, and the only remote party is the model provider, when one is configured;
- no protection against a compromised local user account — a process running as the developer can read `$DEBUGGEN_HOME/auth.json`, the Chrome profile and the project itself, and can send any `Origin` header it likes, so it can do anything the developer can;
- no automatic repair of the bugs the tool finds — it reports observations and likely causes and never edits code to fix them.

## 2. What is captured, and what is never captured

Capture is scoped in time and by plan. The browser agent is **dormant** until the Chrome service worker relays an `agent.config` for a tab bound to a session, and returns to dormant when a later configuration clears every hook. The Node preload admits a span only while a capture is open and only for the signals the plan enabled (`packages/telemetry/src/node/control.ts`). The service drops any batch it cannot attribute to a bound session's open capture before parsing it (`apps/local-service/src/telemetry/attribute.ts`, `ingest.ts`).

### 2.1 Browser tier — the page agent (`packages/telemetry/src/browser/*`)

| Signal                          | What is recorded                                                                                                                                                                                       | Source                            |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------- |
| Interactions                    | event type (`pointerdown`, `click`, `keydown`, `submit`, `change`), handler timing from the Event Timing API, target selector and tag, up to 80 characters of scrubbed visible text, React owner chain | `interaction.ts`, `dom-target.ts` |
| React renders and commits       | component display name, phase, duration, render count, changed prop **key names**, trigger classification                                                                                              | `react.ts`, `fiber-diff.ts`       |
| State transitions               | component, hook index, and a type plus 120-character redacted preview of the old and new value                                                                                                         | `state.ts`, `fiber-diff.ts`       |
| Component-tree snapshot         | component names in owner/parent order with per-node render counts                                                                                                                                      | `react.ts`                        |
| `fetch` / XHR metadata          | method, redacted URL, status, size, timing, and the call-site stack (with its URLs' query values masked) for click-to-source                                                                           | `fetch.ts`                        |
| Performance entries, long tasks | `navigation`, `resource`, `paint` and `longtask` entries: names, timings, sizes                                                                                                                        | `perf.ts`                         |
| JavaScript errors               | exceptions, unhandled rejections and resource-load errors: message and stack, scrubbed, stack URLs masked                                                                                              | `errors.ts`                       |

### 2.2 Server tier — Next.js's tracer plus the Node preload (`packages/telemetry/src/node/*`)

| Signal                      | What is recorded                                                                                                                     | Source                                                                     |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| Incoming HTTP requests      | `http.server` spans: method, route, status, timing                                                                                   | Next.js's own tracer, active once `register.ts` installs a tracer provider |
| Route handlers              | `route.handler` spans                                                                                                                | Next.js's own tracer                                                       |
| Outgoing fetch              | `http.client` spans: method, redacted URL, status, timing                                                                            | Next.js's own tracer                                                       |
| Functions the plan selected | `function` spans for the named symbols a plan patched ([section 6](#6-generated-instrumentation-risks-and-reversibility-guarantees)) | `span-helper.ts` behind the patch template                                 |

### 2.3 Database tier

| Signal         | What is recorded                                                        | Source                              |
| -------------- | ----------------------------------------------------------------------- | ----------------------------------- |
| Prisma queries | `db.query` spans: parameterised statement text, duration, `db.rowCount` | `@prisma/instrumentation`           |
| `pg` queries   | `db.query` spans: parameterised statement text, duration, `db.rowCount` | `@opentelemetry/instrumentation-pg` |

### 2.4 Never captured

- **Request and response bodies.** Only method, redacted URL, status, size and timing. The fetch/XHR patch reads no body, clones nothing and never reads a header value; the only header it adds is `traceparent`, on same-origin requests (`packages/telemetry/src/browser/fetch.ts`). Any attribute named like a body, payload, result set or parameter list is dropped outright at ingest (`DROPPED_ATTRIBUTE_KEYS` in `packages/telemetry/src/redaction/redactor.ts`).
- **Full React prop and state values.** Props and state are captured as key names plus a type/summary and change flags. Previews are truncated to 120 characters after passing through the same pattern rules as every other value, each object is bounded to 32 keys, and functions and DOM nodes are never serialised (`MAX_PREVIEW_LENGTH` and `MAX_TRACKED_KEYS` in `packages/telemetry/src/schema/attributes.ts`; `packages/telemetry/src/browser/fiber-diff.ts`). Opt-in full values are not implemented.
- **Database row contents.** Only `db.rowCount`.
- **`.env*` files, `DATABASE_URL` and passwords.** The indexer never reads an `.env` or `.env.*` file, a dot-directory, or the generated and vendored trees `node_modules`, `.next`, `dist`, `out`, `build`, `coverage`, `generated` and their kin, and it reads only TypeScript and JavaScript source extensions (`EXCLUDED_DIRECTORY_NAMES`, `INDEXABLE_EXTENSIONS` in `packages/code-analysis/src/project.ts`). A code excerpt can never be taken from an environment file.
- **Keystrokes, form values, clipboard, screenshots and page HTML.** The interaction listener records the event type, never which key was pressed. The element descriptor reads only `id`, `class` and bounded visible text — never `value`, `innerHTML`, `outerHTML` or `data-*` attributes (`packages/telemetry/src/browser/dom-target.ts`). Nothing reads the clipboard or takes a screenshot.

### 2.5 Where captured data goes

After redaction, and only after it, an event is persisted in the local `node:sqlite` store at `$DEBUGGEN_HOME/sessions.sqlite`, streamed to the DevTools live tail (`telemetry.tail`) and aggregated for the generated panel. What of it may reach a model provider is bounded in [section 4](#4-what-may-leave-the-machine-and-when).

## 3. Redaction

### 3.1 Where it runs

Redaction runs at **two pipeline points**, and a third layer protects the logs:

1. **Ingest, before anything is stored or shown.** `apps/local-service/src/telemetry/ingest.ts` runs, for every batch: attribute the batch → parse each event → compute `request_key` ([section 3.3](#33-the-pre-redaction-request-key)) → **redact** (`redactEvent` in `packages/telemetry/src/redaction/redactor.ts`) → stamp session and capture → persist → correlate → live tail. Nothing downstream — the store, the aggregates, the panel data routes, the DevTools panel — ever sees an unredacted value, and an event the redactor cannot process is counted and never stored.
2. **Every outbound prompt payload.** `packages/model-provider/src/redact-guard.ts` re-inspects the whole request — system text, rendered prompt, prior messages and structured input — and **rejects the call** when a denied pattern survived. Besides the credential shapes and the denied header keys, it reads every string for two shapes that sit inside prose. One is a URL that still carries an unmasked query value — any absolute `http(s)` URL, and an origin-relative `/path?…` at the start of the text or after whitespace, a written whitespace escape (`\n`, `\r`, `\t`, `\f`, `\u000b`) or `(`, each read up to whitespace, a quote, an angle bracket, a backtick, or a written whitespace or quote escape of a JSON-rendered prompt section (any other backslash, `\u005a` included, stays part of the value) — where a value counts as masked only when it is empty, `?`, `…` or `?…`, or, inside a stack frame, a masked value followed by its `:line:column`. The other is a header line that still carries a credential, at the start of the text, after a character that cannot be part of a header name, or after a written whitespace escape: `authorization` or `proxy-authorization` followed by a scheme word (`Bearer`, `Basic`, `Digest`, `Negotiate`, `NTLM`) and a credential, `cookie` followed by any pair with a value, quoted or not, or `set-cookie` followed by a first pair with a value, or `x-api-key` or `x-auth-token` followed by a credential. It is a guard, not a second redactor: it never rewrites a payload, so a regression upstream fails loudly instead of being hidden. It also **fails closed**: a payload too deep or too large to inspect completely is refused, and so is a string with more than 8,192 URL runs that can carry a value (`max-url-runs`) or with one such run longer than 4,096 characters (`max-url-length`); a finding names the field path and rule, never the value. The guard runs when the local service builds each stage request (`apps/local-service/src/pipeline/context-builder.ts`, `src/panels/generate.ts`) and again inside the network provider before transport, including on every repair turn (`packages/model-provider/src/providers/anthropic.ts`).
3. **Logs.** `apps/local-service/src/logging.ts` applies pino's path-based `redact` option and then walks every field and message through the same scrub primitives, so a credential inside an error message a library wrote is removed before the record is written.

The redaction functions are pure — no I/O, clock or randomness — and unit-tested per handler (`packages/telemetry/src/redaction/*.test.ts`, `packages/model-provider/src/redact-guard.test.ts`). Attribute **names** are judged as well as values, because a page can use a token as a map key.

### 3.2 Deny list

The rule vocabulary is `sensitive-header`, `provider-key`, `bearer-token`, `jwt`, `private-key`, `connection-string`, `url-query-value` and `entropy` (`REDACTION_RULE_IDS` in `packages/telemetry/src/redaction/rules.ts`). The literal patterns live in three places — `packages/telemetry/src/redaction/rules.ts` for runtime redaction, `packages/model-provider/src/redact-guard.ts` (`CONTENT_PATTERNS`: provider keys, bearer tokens, JWT shapes, private-key headers and credentialed connection strings; `HEADER_LINE_PATTERN`: sensitive header lines in text; `EMBEDDED_URL_PATTERNS`: URLs embedded in text) for the outbound prompt guard, and `scripts/check-secrets.mjs` for the repository gate — and all three assemble them from fragments so that none of the files contains a matchable secret; this document names them rather than repeating them. The three are kept consistent by convention and by their tests, not by an import edge: `@debuggen/model-provider` depends on no workspace package but `@debuggen/shared`, and the gate script sits outside every workspace. Changing a credential pattern therefore means changing every one of the three files that carries it — all three for provider keys, JWT shapes, private-key headers and credentialed connection strings; the telemetry rules and the guard for bearer tokens and sensitive header lines, which the gate does not scan for — and updating each one's regression suite: `packages/telemetry/src/redaction/rules.test.ts` and the other `packages/telemetry/src/redaction/*.test.ts` suites, `packages/model-provider/src/redact-guard.test.ts` and `scripts/check-secrets.test.mjs`. The embedded-URL grammar is held twice in the same way, in `packages/telemetry/src/redaction/url.ts` and the guard, and the two change together. `apps/local-service/src/logging.ts` holds no fourth set: it reuses the telemetry scrub primitives.

| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- |

**URLs inside text.** Free text — every string attribute under any key, React prop and state previews, event names other than a database query's, the selected element's descriptor and the developer's question — takes `redactTextUrls`, which masks absolute, origin-relative, bare-relative and quoted URLs alike, and masks punctuation at the end of a query with it because the punctuation may be part of the value (`/reset?code=!!!!` becomes `/reset?code=?`, `See /p?id=7.` becomes `See /p?id=?`). The strings a stage sends that may be source code — code excerpts, tool results, model-authored text — take `redactEmbeddedUrls` instead, which masks only absolute `http(s)` URLs and origin-relative `/path?…` runs at the start of the text or after whitespace or `(`; that keeps optional chaining, ternaries and regular expressions in an excerpt intact ([section 3.4](#34-residual-risk)). Stack text (`error.stack`, a request's `initiator`, a `componentStack`) takes `redactStackText`: every line — the thrown error's message, its continuations and every frame — is masked as free text, so a stack never carries a query value its `error.message` lost, and a line the runtime wrote as a frame (classified by the whole line) keeps only the `:line:column` after its masked query, so source-map resolution still works. The text maskers also anchor a URL after a written whitespace escape (`\n`), which is how the guard reads a JSON-rendered prompt section.

### 3.3 The pre-redaction request key

Duplicate-request detection is the one place raw URL data is used, and it is used exactly once. Redaction stores `?id=A` and `?id=B` identically as `?id=?`, so grouping by the stored URL would report two distinct requests as a duplicate. `packages/telemetry/src/redaction/request-key.ts` therefore computes, at ingest and **before** redaction:

```text
request_key = HMAC-SHA-256(sessionKey, version + method + path + sorted query pairs)
```

The input is the unredacted URL; the key is 32 random bytes generated per session and held only in the store's `session_keys` table, never sent anywhere. Byte-identical requests collide, so genuine duplicates are detected; requests that differ only in a parameter value do not, so distinct requests are never merged. The raw URL is never stored or displayed, the digest is opaque — the material it was computed over cannot be recovered from it — and the session key is deleted with its session. `packages/telemetry/src/aggregate/requests.ts` groups by `request_key`, and `request-key.test.ts` pins both the duplicate and the distinct-parameter cases.

### 3.4 Residual risk

Pattern-based redaction is best-effort against data the application itself places in URL paths, header names, span names, error messages, element text or SQL identifiers: a customer email in a path segment, for example, is not a pattern this layer recognises. Four known limits of the text rules follow from keeping them usable on prose and code:

- a bare `bearer` followed by a credential shorter than 8 characters, outside a header line, is neither masked nor refused, because a short word after "bearer" is ordinary English;
- in the strings a stage sends that may be source code, only the anchored URLs of [section 3.2](#32-deny-list) are masked, so a path inside a quoted string or template literal (`'/api/x?a=1'`), a bare-relative `p?id=1` and a query-only `?id=1` keep their query text, and the outbound guard checks the same anchored subset, so it does not refuse them;
- a header written as a quoted key inside text (`{"cookie":"session=abc"}` in a log line or a prompt) is not a header line to either text rule, which allow only blanks between the name and its colon, so its value survives unless another rule matches it, such as a bearer credential of 8 or more characters; structured headers are unaffected — a header attribute, a header-map member and an attribute named for a denied header are masked at ingest, and a denied header name used as a structured key with any value but `[redacted]` is refused by the guard;
- a string that is a single token once trimmed and holds a masked query followed by a quote (`/reset?code=?'x`) is read by the guard as one URL whose value runs past the quote, and is refused although the text maskers end the query at the quote; the failure is closed — the stage fails, nothing leaves.

The mitigations are structural rather than pattern-based — bodies, row contents, input values and full prop/state values are never read at all, every preview is bounded, and the outbound guard fails closed. For a codebase whose runtime data must not leave the machine under any circumstances, run with `DEBUGGEN_PROVIDER=deterministic` ([section 4](#4-what-may-leave-the-machine-and-when)).

## 4. What may leave the machine, and when

**Nothing leaves the machine unless the `anthropic` provider is selected and both `ANTHROPIC_API_KEY` and `DEBUGGEN_MODEL` are set; nothing leaves at all with `DEBUGGEN_PROVIDER=deterministic`.** The deterministic provider is rules-based and imports no model SDK, opens no socket, reads no environment variable and touches no file (`packages/model-provider/src/providers/deterministic.ts`). With `anthropic` selected but either variable missing, the service reports a configuration failure before any call is attempted (`packages/model-provider/src/factory.ts`).

Know which provider is in effect. The service's own default is `deterministic` (`DEFAULT_PROVIDER_ID` in `factory.ts`, and `.env.example`). When the VS Code extension starts the bundled service, it chooses the child's `DEBUGGEN_PROVIDER` by precedence (`resolveProviderSetting` in `apps/vscode-extension/src/service/process.ts`): a `debuggen.provider` value set explicitly in user, workspace or folder settings is forwarded; otherwise a non-empty `DEBUGGEN_PROVIDER` inherited by the editor is left in place; otherwise the setting's manifest default, `anthropic`, is forwarded. The setting has `machine-overridable` scope, so a workspace's own settings can set it too, and an explicit value there overrides a `deterministic` inherited from your shell (`apps/vscode-extension/package.json`). A service you start yourself is unaffected by the setting. Set `debuggen.provider` to `deterministic` to keep a session entirely local, review the `.vscode/settings.json` of a repository you do not trust, and before sending anything confirm the provider the running service reports: at the default `info` log level it logs `model provider and prompts ready` with its `provider` when it starts, in the **Debug Generator Service** output channel when the extension started it. The automated suites pin the provider themselves: `playwright.config.ts` starts its service with `deterministic` unless `DEBUGGEN_PROVIDER` is exported in the shell, and the extension-host harness (`apps/vscode-extension/.vscode-test.mjs`) removes every inherited `DEBUGGEN_*` and `ANTHROPIC_*` variable and sets `deterministic`; the README's [test-suite variables](../README.md#test-suites) list every control those suites read.

When a provider is configured, each stage sends only the following, after the redaction and caps in `apps/local-service/src/pipeline/context-builder.ts` (`src/panels/generate.ts` for panel generation) and the outbound guard of [section 3.1](#31-where-it-runs). The developer's question and a follow-up question are redacted before they are rendered into any prompt — credential shapes replaced, a sensitive header line's value replaced and every URL query value masked (`scrub`, then `redactTextUrls`) — and every string of a stage's structured input, code excerpts and tool results included, passes the code-safe URL masker of [section 3.2](#32-deny-list).

| Stage                    | What is sent                                                                                                                                                                                                                                                                                                                                                                             |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Problem understanding    | the developer's question, redacted, in the prompt text, and in the structured input only lexical hints derived from the redacted question; the selected target descriptor (selector, tag, up to 120 characters of visible text, component chain, URL), every string scrubbed and URL-masked; the current URL, redacted; the project summary from `packages/code-analysis/src/summary.ts` |
| Code investigation       | the redacted question, the understanding, and the results of read-only code-graph queries the model proposes and deterministic code executes: names, file paths, relations and **bounded excerpts of only the files the investigation selected** (at most 40 lines and 4,000 characters each, `CODE_QUERY_LIMITS` in `packages/code-analysis/src/graph/query.ts`)                        |
| Instrumentation planning | the understanding, the investigation and the adapters' capability catalog                                                                                                                                                                                                                                                                                                                |
| Analysis                 | the redacted question (on a follow-up, the follow-up question); aggregate telemetry statistics — trace trees, top spans, render statistics, request and query groups — with redacted span attributes and the relevant bounded excerpts                                                                                                                                                   |
| Panel generation         | the redacted question and any follow-up question; the validated analysis result, the panel node catalog and a bounded capture overview (event, tier and kind counts, metrics, and the top spans, renders, request and query groups and errors from the capture summary), the analysis and the overview URL-masked                                                                        |
| Follow-up                | the prior understanding, plan, capture summary, analysis and panel, and the new question, redacted                                                                                                                                                                                                                                                                                       |

Not sent, even with a provider configured: no repository dump or bulk upload (the investigation stage proposes graph queries; it never receives the tree); no `.env*` content; no request or response bodies; no database rows; no full prop or state values; and no payload that failed the outbound guard. A credential a developer hard-coded in a source file is not rewritten out of an excerpt: the guard refuses the whole call and the stage fails with a finding that names the field, so a secret in source makes a stage fail rather than leak.

The egress path is `packages/model-provider/src/providers/anthropic.ts`, which calls the Anthropic API over HTTPS through `@anthropic-ai/sdk`, authenticated with `ANTHROPIC_API_KEY` read from the service's environment. The model id comes from `DEBUGGEN_MODEL` and is never hardcoded or defaulted, so a session's record of the model it used is always true. What was sent is auditable after the fact: prompts are versioned files and the versions used are recorded on the session ([section 5](#5-model-provider-boundary)).

## 5. Model provider boundary

**One interface, two implementations.** `ModelProvider` (`packages/model-provider/src/provider.ts`) has a network-backed implementation, `providers/anthropic.ts`, and a rules-based one, `providers/deterministic.ts`, which builds schema-valid outputs from the structured inputs — code-graph candidates and capture aggregates — and never reads the rendered prompt or the question's wording. `factory.ts` selects between them from `DEBUGGEN_PROVIDER`. Every automated test uses the deterministic provider, and **no recorded model responses are shipped** anywhere in the repository.

**Prompts are versioned, auditable files.** Each stage's prompt is a repository file, `apps/local-service/prompts/<stage>/vNNN.md`, treated as immutable once committed: a change is a new version file plus an update to `prompts/manifest.json`, which selects the current version per stage. `packages/model-provider/src/prompt-loader.ts` loads by stage and version, and the versions used are recorded on the session (`promptVersions` in `packages/protocol/src/session-record.ts`). No prompt strings live in modules, so what a session asked a model is reconstructible from the repository and the session record, and a prompt change is always a reviewed diff.

**The model cannot act.** It produces data, and that data is schema-validated before it can affect anything:

- The only code that writes to the developer's project is `packages/instrumentation/src/patch/patcher.ts` and `packages/instrumentation/src/cleanup.ts`, invoked by `apps/local-service/src/instrumentation/service.ts` with a validated, normalised plan whose actions have passed the feasibility check against the code graph (`packages/instrumentation/src/feasibility.ts`).
- The investigation stage's "tools" are read-only code-graph queries executed by `apps/local-service/src/pipeline/tools/code-tools.ts`; the model proposes, deterministic code executes.
- No model output is evaluated, executed or rendered as markup. A generated panel composes only components registered in the node catalog (`packages/panel-schema/src/catalog.ts`, `packages/panel-renderer/src/host/registry.ts`); an unknown node type fails validation before rendering, and all model text is rendered as text.

**Validation, then safe fallbacks.** Output is parsed against the stage's authoring schema with at most two repair re-prompts (`DEFAULT_MAX_REPAIRS`, `packages/model-provider/src/structured.ts`), then passed through deterministic normalisation and the internal schema; a failure there is a rejection, never retried against the model. A rejected plan falls back to a runtime-only default plan built from the adapters' capabilities (`apps/local-service/src/pipeline/stages/plan.ts`), which patches no file. A rejected panel falls back to a deterministic panel assembled from the capture aggregates (`apps/local-service/src/panels/fallback.ts`), flagged `meta.fallback` and shown under the banner "Generated panel failed validation; showing a fallback view built from captured data." Observed facts must cite evidence that exists in the capture (`packages/panel-schema/src/semantic.ts`). A session reaches `generated` only after a validated analysis and a validated panel exist (`apps/local-service/src/sessions/state-machine.ts`), so a failure is never presented as a successful analysis.

## 6. Generated instrumentation: risks and reversibility guarantees

### 6.1 The risk

This product **edits files in the developer's working tree.** When a plan asks for the timing of a named function — the one signal runtime hooks cannot supply — that function's body is moved into an inner function and wrapped with a call to a span helper (`packages/instrumentation/src/patch/function-timing.ts`, `wrap-template.ts`). Three things could go wrong, and each has a specific mitigation:

| What could go wrong                                                  | Mitigation                                                                                                                                                                                              | Enforced by                                                                                           |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| An edit is left behind after a session, a crash or an editor restart | every edit is journalled before it is written, and cleanup reconciles every open record on end, on editor deactivation and on service start                                                             | `packages/instrumentation/src/patch/patcher.ts`, `apps/local-service/src/cleanup/cleanup.ts`          |
| An edit collides with the developer's own change to the same file    | a file whose bytes differ from what the tool wrote is never modified; it is reported as a conflict                                                                                                      | `apps/local-service/src/instrumentation/watcher.ts`, `packages/instrumentation/src/patch/conflict.ts` |
| The process dies between taking the backup and writing the file      | the journal records both the original and the expected post-write hash before the write, so reconciliation can always tell "never written", "written but unmarked" and "changed by the developer" apart | `patcher.ts`, `patcher.test.ts` (failure injected at every boundary)                                  |

### 6.2 The guarantees

- **Runtime first.** Patches are used only for `function-timing` and `server-span` actions on named symbols. Every other signal — interactions, renders, requests, performance, errors, server request and route spans, database queries — comes from a runtime hook that touches no file ([section 2](#2-what-is-captured-and-what-is-never-captured)).
- **Original content and hash recorded before any edit.** `patcher.ts` resolves the target inside the project root lexically and then on the filesystem and pins its directory, so a symlink cannot redirect the write outside the project; computes `originalHash` and, from the in-memory patch, `instrumentedHash`; copies the original bytes to `$DEBUGGEN_HOME/backups/<sessionId>/<originalHash>` (mode `0600`) and `fsync`s it (`backup-store.ts`); journals a `ModificationRecord` as `pending` with both hashes, the backup path and the unified diff; and only then writes a temp file, `fsync`s it, re-checks the target and renames it into place atomically, preserving the file's mode.
- **Every modification is visible.** Each record appears in the VS Code modifications list with its diff (`ModificationsList`, `DiffView`), in the DevTools session summary (`SessionSummary`), in the `instrumentation.ready` message, and at `GET /sessions/:id/modifications`.
- **Cleanup is reliable.** `apps/local-service/src/cleanup/cleanup.ts` runs on `session.end`, on VS Code deactivation (which ends the active session over the same route) and as reconciliation on service start — for every non-reverted record, whatever its session's status. Restoration happens strictly in reverse order along follow-up chains, a restored file's hash is verified against `originalHash`, and only then is its backup deleted.
- **Conflicting developer edits are detected, never overwritten.** `watcher.ts` moves a record whose file stops matching `instrumentedHash` to `conflict` and tells both UIs: "‹file› was edited while instrumented. Debug Generator will not overwrite it. Original saved at ‹backup path›." At cleanup, `conflict.ts` authorises a write only when the file still matches what the tool wrote; any other state leaves the file untouched, keeps the original in the backup directory and reports the conflict with diffs, and the session's cleanup status becomes `conflict`.
- **No bookkeeping inside the project.** The session database, backups and index caches live under `$DEBUGGEN_HOME` (default `~/.debuggen`), so a session never changes the project's `git status` beyond the patched files themselves.
- **Teardown disables rather than idles.** When a capture ends, the browser agent returns to dormant: listeners detached, `fetch` and `XMLHttpRequest` restored to the original functions, React hooks unsubscribed. The Node preload stops creating spans at all (a sampler decision, so no span object is even constructed), calls `disable()` on the pg and Prisma instrumentations, and disables the global tracer provider and propagator so Next.js's own spans become no-ops (`packages/telemetry/src/node/control.ts`; `control.test.ts` asserts zero `onStart` calls after disable).
- **Enforced in CI.** `pnpm check:no-residual-instrumentation` (`scripts/check-no-residual-instrumentation.mjs`) fails when an instrumentation marker appears in the demo application's tracked source or its working tree is dirty; `tests/e2e/cleanup.spec.ts` asserts every instrumented file is byte-identical to its pre-session content and that the application keeps serving.

**What remains after cleanup.** An inert preload module stays loaded in the dev-server process — no active patches, no tracer provider and no file changes — and the application keeps serving. A fully instrumentation-free process is restored by **restarting the dev server without the tool**.

### 6.3 Changes to the running application

While a capture is armed, the page agent patches `window.fetch` and `XMLHttpRequest` to add a W3C `traceparent` header to **same-origin** requests only, so no trace context reaches a third-party origin (`packages/telemetry/src/browser/fetch.ts`). It adds no other header, reads no header value or body, returns the same `Response` instance and rethrows the same errors, and on any internal failure calls the original function unchanged. The page's own error handlers are never replaced (`packages/telemetry/src/browser/errors.ts`).

### 6.4 The launched dev server

The service can start the project's dev server itself (`apps/local-service/src/dev-server/launcher.ts`), spawning it without a shell on POSIX, appending the preload to `NODE_OPTIONS` and injecting `DEBUGGEN_INGEST_URL`, `DEBUGGEN_TOKEN` and `DEBUGGEN_PROJECT_ROOT`. The child's output is scrubbed of the token before it is logged or buffered, and the credential is revoked when the child exits ([section 7](#7-local-service-access-boundary)). Without a valid credential the preload stays inert.

### 6.5 Source-open containment

Click-to-source crosses independent containment checks, because the path a panel sends is data from a browser tab:

- **The service.** `apps/local-service/src/source/open.ts` validates the `source.open` frame, refuses one that already carries `pinned`, looks up the session, checks that the requesting principal may act on it, and proves — lexically and on the filesystem — that the file lies inside the session's `projectRoot`. It forwards the location to the session's VS Code client with `pinned: { file, dev, ino }`: the canonical project-relative path and the device and inode of the regular file it proved.
- **The editor.** `apps/vscode-extension/src/source/open-location.ts` is the sink of every session-scoped open — a forwarded `source.open`, the `debuggen.openSource` command and the session view's `openFile` frame. It resolves the session root and the target with `fs.realpath` (a link that leaves the project at any component is refused), requires a regular file, requires a forwarded frame's resolution to equal its pin (a frame without one is refused), opens the canonical path `O_NOFOLLOW` and checks the descriptor's identity, and — holding that descriptor — loads the document unshown, re-checks after the load that the path still names that inode, compares the document with the bytes read through the descriptor, and reveals that same verified document. A link re-pointed while the frame was in flight, or between the check and the editor's own read, is therefore refused rather than shown. Model-suggested locations are held to the same rule before an analysis is accepted (`apps/local-service/src/analysis/facts.ts`).
- **The `vscode://` fallback.** The DevTools panel (`apps/chrome-extension/src/panel/actions.ts`) opens `vscode://debuggen.debug-generator/open?file=…&line=…&col=…` only after the service validated the location and answered `source.result` with `no-editor` because no VS Code window for the project is connected; a location the service refused never falls back to the URI. Any web page can trigger a `vscode://` URI, so `apps/vscode-extension/src/uri-handler.ts` trusts nothing, including the service: it requires exactly one each of `file`, `line` and `col`; refuses traversal, absolute, drive-lettered, UNC, backslash and `~` paths; range-checks line and column; resolves both the workspace folder and the file with `fs.realpath` and requires the file to stay inside an open folder (a symlink that escapes is refused) and to be a regular file; allows one pending dialog at a time; asks the developer to confirm "Open ‹file›:‹line›?" in a modal dialog; and re-validates after the answer before opening. `apps/vscode-extension/test/suite/uri-handler.test.ts` asserts that a file outside the workspace or a traversal path opens nothing.

The panel reports a click's outcome without echoing it. It shows success only when VS Code confirmed it opened the location or the fallback URI was handed to VS Code, and every failure as fixed copy for its error code (plus a reference for an unexpected error), never the raw error text, so a refused path or an internal error message cannot surface in the DevTools panel (CWE-209). The refusal never reaches another tab either: the service sends a handler refusal only to the requesting connection, and the service worker (`apps/chrome-extension/src/background/service-worker.ts`) passes the requesting panel the error code with a fixed sentence and withholds a correlated `error` frame from every panel. To keep recognising those frames it never forgets a request still awaiting its answer; past 256 unanswered requests it refuses new clicks (`RATE_LIMITED`) before sending them.

## 7. Local service access boundary

Binding to `127.0.0.1` keeps other machines out, not other local processes or web pages, so the service authenticates every client, binds every credential to a role and a scope, and refuses every web origin. The mechanism is `apps/local-service/src/server/auth.ts`; every route and socket consumes its decisions.

### 7.1 Three role-bound credentials

Each credential is 32 random bytes from a CSPRNG, rendered base64url, and stored **only as its SHA-256 hash** in the `credentials` table together with its role, scope, issue time and optional expiry (`CREDENTIAL_ROLES`, `CREDENTIAL_TOKEN_BYTES`).

| Role           | Scope                                                                                                    | Issued by                                                                                                                                                                                         | Plaintext held                                                                                        | Lifetime                                                                                                                                                                                    |
| -------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `vscode`       | the machine user; acts only under the workspace folders its live connections announced in `client.hello` | the service on first start                                                                                                                                                                        | `$DEBUGGEN_HOME/auth.json` (mode `0600`), read directly by the extension, which runs as the same user | until rotation                                                                                                                                                                              |
| `devtools`     | the Chrome extension id that redeemed a pairing code                                                     | `POST /pair/complete`                                                                                                                                                                             | that one response, then `chrome.storage.local` (`apps/chrome-extension/src/background/auth.ts`)       | until rotation                                                                                                                                                                              |
| `server-agent` | exactly one `projectRoot`                                                                                | the dev-server launcher, once per launch; or `POST /dev-server/credential` (`devServer.credential`, a row of protocol's route table; editor credential required) for a dev server started by hand | the dev-server process environment, as `DEBUGGEN_TOKEN`                                               | revoked when its process exits; a hand-started server's, when its holder releases it through `POST /credentials/release` after the server exits, or else 20 s after its preload disconnects |

A hand-started dev server's `server-agent` credential is a supervised lease (`DEFAULT_CLI_CREDENTIAL_LEASE_MS`, `CLI_CREDENTIAL_DISCONNECT_GRACE_MS` in `apps/local-service/src/dev-server/launcher.ts`): `POST /dev-server/credential` answers with the end of a five-minute first lease, the launcher renews it while a `server-agent` control connection authenticated with it is online, and it revokes the credential 20 seconds after that connection is gone — the dev server exited — at the end of the first lease when no preload ever connected with it, and when the service shuts down. A lease nothing renews (the service crashed) stops authenticating within five minutes. Its holder need not wait for any of that: it releases the credential early through `POST /credentials/release` (`credentials.release`, editor credential only, [section 7.7](#77-rotation-and-revocation)), and `scripts/dev-instrumented.mjs --spawn-local` does so once its dev server has exited, after proving the service's identity again ([section 7.3](#73-the-two-unauthenticated-operations)). A release that fails is only a warning, and one that never happens (the command was killed) leaves the credential to the supervision above, which remains the fallback.

The page agent holds no credential and no socket: the service worker relays its frames under the tab's `devtools` connection, and a `client.hello` claiming to be the page agent is refused.

### 7.2 Presentation

Every HTTP request carries `Authorization: Bearer <token>`. Every WebSocket must send its token in its first frame, `client.hello`, within 3 seconds of the upgrade, or it is closed with code **4401** (`CLIENT_HELLO_TIMEOUT_MS`, `WS_CLOSE_UNAUTHORIZED` in `packages/protocol/src/messages/agent.ts`). The stored role and scope become the request's principal; the `client`, `projectRoot` and `tabId` a hello announces are claims, and where a claim contradicts the credential the connection is refused. Authorization therefore never depends on a client's self-description. Each role may also be presented only from the origin its client can have: an editor credential from no origin or a VS Code webview, a DevTools credential from `chrome-extension://<the id it was issued to>`, and a server-agent credential only from no origin. Chrome sends no `Origin` on a `GET` the extension's service worker makes to a host it holds a permission for, and an `Origin` header is only a claim: any local process holding a credential can write the extension's origin itself. So the four read-only `GET` routes a DevTools credential may call (`session.get`, `panel.get`, `panel.getById`, `modifications.list`) also require a **read proof**, a second secret issued with the credential when the pairing code is redeemed. `POST /pair/complete` draws 32 random bytes (43 base64url characters, `readProofSchema` in `packages/protocol/src/http.ts`) with the token, returns both exactly once, and keeps only the proof's SHA-256 digest, inside the credential's own row of the `credentials` table. The service worker stores the proof with the token in `chrome.storage.local` and presents it as `x-debuggen-read-proof` (`READ_PROOF_HEADER`) on each of those reads. Every DevTools read must carry it, from no origin and from the issuing extension's origin alike. Without it, with a malformed value or several headers, or with any proof other than the one issued with that credential (including a credential paired before read proofs existed), the read is refused as `UNAUTHORIZED` (401), which the extension answers by dropping its pairing so the developer pairs again. Nothing sent on a connection registers or replaces a proof, and a `client.hello` carrying one is refused. So a stolen DevTools token alone reads nothing, whatever `Origin` it writes and whatever hello it sends: only the caller that redeemed the pairing code ever held the proof. Rotation deletes the credential row, and the digest with it. The header on any request other than those four reads is refused. Every state-changing request and every `client.hello` must still come from the issuing extension's origin. No web page can use any of this: a page's own cross-origin request names its origin, and the no-origin requests a page can provoke cannot carry an `Authorization` header.

### 7.3 The two unauthenticated operations

- `GET /health` returns `{ version, protocolVersion, pairingAvailable }` and nothing else. A probe that sends an `X-Debuggen-Identity-Challenge` also receives `X-Debuggen-Identity-Proof` and `X-Debuggen-Identity-Endpoint`: an HMAC-SHA256 keyed by the editor credential in `auth.json` over the challenge and the service's own bound `host:port` (`apps/local-service/src/server/routes/health.ts`). The service answers the challenge only when `DEBUGGEN_HOST` is an IP address, because a name such as `localhost` can stand for more than one listener. It lets a client authenticate the service before sending it a credential — `scripts/dev-instrumented.mjs` dials addresses only (it resolves `localhost` itself and probes each loopback address), sends the editor credential only to the address whose proof verifies and names exactly that address and port, and sends every later request there — and it discloses neither the credential nor its hash. Any failure to produce it only omits the two headers.
- `POST /pair/complete { code }`, whose one-time code **is** the capability: 8 characters from a CSPRNG over a 32-symbol alphabet without look-alike characters, valid for 5 minutes, redeemable once, stored only as a hash in `pairing_codes`, compared exactly as sent (no trimming, no case folding: the DevTools pair dialog normalises what the developer typed before it submits, and any other spelling is a wrong guess), and rate-limited by a single service-wide lockout — 5 failed redemptions, each within 60 seconds of the one before, lock pairing for every caller for 60 seconds, during which even the right code is refused (`429`) and nothing is burned; a success or a quiet minute clears the count. The count is never keyed by the caller-controlled `Origin`, so a local process that forges extension ids gets no more guesses than one that does not, and since every client reaches the loopback service from the same address, the one ledger is the peer throttle. The credential a redemption issues is still scoped to the redeeming extension's id (`PAIRING_*` constants in `auth.ts`).

Both refuse web origins like every other route: the origin policy runs before the exemption check, so "exempt" means "no bearer credential", never "unprotected" (`AUTH_EXEMPT_OPERATIONS` in `packages/protocol/src/http.ts`).

### 7.4 Pairing the Chrome extension

The Chrome extension cannot read `auth.json`, so it pairs (`apps/local-service/src/server/routes/pair.ts`):

1. The VS Code command `debuggen.pairChrome` calls `POST /pair/start` with the editor credential and shows the code.
2. The developer types the code into the DevTools panel's pair dialog.
3. The service worker calls `POST /pair/complete` from its `chrome-extension://<id>` origin and receives a `devtools` credential scoped to that id — taken from the validated `Origin` header, never from the request body — together with the read proof issued with it, and stores both in `chrome.storage.local`.

A DevTools credential presented from any other origin is rejected. From no origin at all it is accepted only on the read-only `GET` routes of §7.2. Those reads, from either origin, are admitted only with the read proof issued with the credential at pairing.

### 7.5 Origin policy

Any HTTP request or WebSocket upgrade whose `Origin` is an `http:` or `https:` web origin is rejected, as are `file:`, `data:`, `null` and anything unparseable. Accepted origins are exactly three shapes, judged on the parsed URL rather than a prefix: absent (Node clients such as the extension host and the preload), `chrome-extension://<id>` and `vscode-webview://<id>`. **No `Access-Control-Allow-Origin` header is ever set**, so a browser page cannot read any response even if it provokes one, **and** every state-changing route requires a bearer credential, which closes cross-site request forgery. Both halves matter: without the first a page could read responses; without the second a page could still cause effects.

Origin checks constrain browsers, which set `Origin` honestly. A local process can send any header, so against local processes the bearer credential is the control — and a process that can read the developer's files can read that credential ([section 1.4](#14-non-goals)).

### 7.6 Authorization by role and scope

| Role           | May                                                                                                                                                                                                                                                                                             | May not                                                                                      |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `vscode`       | create, question, control and end sessions, launch and stop dev servers, request a server-agent credential, start pairing — for project roots under the workspace folders it announced; rotate every credential, release a `POST /dev-server/credential` credential and run the retention sweep | act on a project outside those folders                                                       |
| `devtools`     | bind its own tab, select targets, read the session, start and stop capture, query panel data and modifications, and send `source.open` — **only for the session bound to that tab**                                                                                                             | create, question or end a session; act on a session bound to another tab; claim a project    |
| `server-agent` | post telemetry to `POST /telemetry/ingest` and receive its own `server-agent.config` — only for its scoped project                                                                                                                                                                              | call any session route; ingest for another project; release any credential, its own included |

The operation-to-role table is `OPERATION_ROLES` in `auth.ts`. Its four administrative operations — `session.purge`, `devServer.credential`, `credentials.release` and `credentials.rotate` — are the editor credential's alone. Those are rows of protocol's route table like every other: the service registers exactly the operations of `HTTP_ROUTES` and no route beside them.

**"That tab" is named on every request, never inferred.** One pairing issues one DevTools credential, and the Chrome service worker presents it for every tab the developer inspects over a single socket, so the credential alone cannot say which tab is asking. The worker therefore names the acting tab — taken from Chrome's own port metadata, never from a page — on every session-scoped HTTP request (the `x-debuggen-tab` header, `ACTING_TAB_HEADER` in `packages/protocol/src/http.ts`) and on every frame it sends for a tab (the envelope's optional `tabId`), and announces no tab in its `client.hello`. `requireBoundSession` in `auth.ts` admits a DevTools action only when the session's live binding is that tab's and was made by the same credential; a request that names no tab, or another tab, is refused with `TAB_NOT_BOUND`. A relayed telemetry batch is attributed only to its acting tab's live binding and is refused, never re-attributed, when that tab has none. A connection whose hello names a tab speaks for that one tab only: its binding, navigation, unbind, readiness, target-selection, source-open and telemetry frames are refused with `TAB_NOT_BOUND` when they name any other tab (`requireAnnouncedTab` and `actingTabOf` in `apps/local-service/src/server/ws.ts`).

Inside the worker, the same rule holds end to end. A DevTools panel keeps the tab it was first associated with: naming another tab's session never moves it there, and its requests for that session are refused locally (`associatePanel` and `checkPanelScope` in `apps/chrome-extension/src/background/service-worker.ts`). A telemetry batch is written only after the service has confirmed its tab's binding on the current connection, never parked in the socket's reconnect queue, and is dropped, with the loss counted in the worker's log, when the tab's binding has moved to another session or capture since the page produced it, or when no confirmation arrives within 30 s of the batch's arrival (`awaitTabRoute` in `ws-bridge.ts`). The page's own session and capture stamp can only cause a drop, never choose where a batch goes.

**An editor's announced folders outlive a dropped socket briefly.** The editor credential acts only under the workspace folders its live connections announced; when the editor's socket closes, those folders stay announced for the socket's offline grace (60 s by default, never more than five minutes) so `session.end` during a disconnect or VS Code shutdown is still authorized. The lease expires on the service clock and is cleared by rotation.

**"Under an announced folder" holds on disk, not only in spelling.** `requireProjectScope` in `auth.ts`, which `requireSessionAccess` re-runs on every session request, and `admitProjectRoot`, on which it is built and which the routes that take a project root from the editor call directly where they must keep the proof, admit a root only when, for one announced folder, the root lies under it both as a normalised path and after both are resolved with `realpath`. So a symlink inside the workspace that points elsewhere (`/work/shop/external` → `/home/dev/private`) cannot carry a session, a dev-server launch or a server-agent credential out of it. A link that stays inside, or a workspace announced through a link, is still admitted. A tail that does not exist yet is kept as spelled beneath its longest existing ancestor. A component that exists as a link to something that does not exist yet — a dangling link — is refused, because where it will lead cannot be established. A root whose real path cannot be established (permission denied, a link loop, a drive-lettered path on a host that is not Windows) is refused. The check holds at the moment it runs, so each place that spawns in, indexes or writes to a root after an `await` re-proves the identity the root was admitted under — synchronously, immediately before it acts — and then acts in that canonical directory rather than through the root's links. `admitProjectRoot` returns the root with its canonical path; `reconfirmProjectRoot` re-proves both the scope and that identity; `reconfirmRootIdentity` re-proves the identity alone, for work that runs after the request has answered and holds no principal (scope for a session is re-run by `requireSessionAccess` on every request that names it). `session.create` (`routes/sessions.ts`) admits the root, judges the state-root separation on its canonical path, re-proves it immediately before the session is stored, and hands the proof to the session manager, which stores its canonical path with the session in the transaction that inserts it (`session_root_identities`, store schema version 6). `dev-server.launch` (`routes/dev-server.ts`) admits the root, re-proves it at its fence, and hands the launcher a confirmation that `dev-server/launcher.ts` runs before it first reads the project and again immediately before the spawn. Detection reads `package.json` and the lockfiles, and the command policy judges script declarations and framework-CLI paths, in the canonical directory the first confirmation proved; the second must prove the same directory, and the child runs in it. The pipeline's indexing (`pipeline/orchestrator.ts`) and every install (`instrumentation/service.ts`) call `SessionManager.confirmProjectRoot` immediately before they act, index that directory and hand it to the patch layer, and `patcher.ts` resolves, pins and writes every patched file inside it and refuses a patch once a directory on its path has been replaced by a link. A link retargeted between admission and any of these acts — even to another directory inside the workspace, which the scope check alone would still admit — is refused with `PATH_OUTSIDE_PROJECT` instead of followed; in the pipeline, that fails the session at the stage that met it. A session read back after a restart is held to its stored identity, so a link retargeted while the service was not running is refused like any other; a session with no stored identity — stored before version 6, or created without a proof — is refused at every sink rather than identified after the fact. Two residues remain. Cleanup restores files through the root as the session records it, without re-proving that identity. A restore writes only over a file that hashes to the recorded instrumented content, so a root relinked after patching receives no write unless it already holds those exact bytes. For an applied modification, any other content or a missing file there is reported as a conflict with the backup kept, and the directory that was patched keeps its instrumentation until the developer restores it from that backup; a modification whose write was never confirmed is closed when the file there already holds the original. Three reads still go through the root as the session spells it: the code index the telemetry ingest resolves source locations from, the one the capture-readiness check reads, and the watcher that hashes patched files to notice edits. A link retargeted under one of those reads can change what is reported, not where anything runs or is written. `apps/local-service/test/integration/auth.test.ts` relinks a launch's root while the launch is under way, a session's root while its pipeline is planning, a session's root after its pipeline reached the readiness gate, and a session's root while the service is stopped, and asserts that the launch spawns nothing, that the install writes to neither directory and fails the session at the instrument stage, and that the session manager — the running one, and the one the restarted service builds — then refuses the root; `dev-server/launcher.test.ts` swaps a launch's root to a decoy for detection and back before the spawn and asserts the decoy's scripts authorize nothing.

### 7.7 Rotation and revocation

The VS Code command `debuggen.rotateServiceToken` calls `POST /credentials/rotate` (`credentials.rotate`), which only the editor credential may call and whose body must be exactly `{}` (`apps/local-service/src/server/routes/credentials.ts`). `AuthService.rotateAll` then rotates everything. The store and `auth.json` share no transaction, so the replacement is journaled, and no file is touched inside the transaction:

1. **Stage.** The new editor credential is written to the journal `$DEBUGGEN_HOME/auth.json.pending`, atomically at mode `0600`.
2. **Commit.** One store transaction deletes every credential and outstanding pairing code and inserts the new editor credential's row.
3. **Publish.** `auth.json` is rewritten from the journal, and the journal is removed.
4. **Revoke.** Every open socket, the caller's own editor socket included, is closed with code 4401.

The reply, `{ credentialsDeleted, socketsClosed }`, is sent last. It still reaches the caller, because it travels on the request's own HTTP connection, and it never carries the new credential: the editor re-reads `auth.json` when its socket closes with 4401 or a request is refused as unauthorized. A failure before the commit leaves every existing credential valid, and the error says so; a failure after it is reported as a rotation that did happen, with a restart hint. A rotation interrupted after its commit is completed at the next service start (or the next rotation): a journal whose credential has a row is published, and one without is discarded, so a retired credential never comes back. Paired Chrome extensions must pair again, and launched dev servers must be relaunched to receive a new server-agent credential. A launched dev server's credential is also revoked on its own the moment the process exits.

`POST /credentials/release` (`credentials.release`) is the narrow counterpart: only the editor credential may call it, its body must be exactly `{ token }`, and it revokes the one `POST /dev-server/credential` credential that token names and closes that credential's sockets with 4401 (`DevServerLauncher.releaseCredential` in `apps/local-service/src/dev-server/launcher.ts`, `AuthService.releaseServerAgentCredential`). The flag reports what that one request did: `{ released: true }` only when it removed a live credential, and `{ released: false }` whenever it released nothing — the token is unknown, already revoked or lapsed, rotated away (even while the service still supervised it), another role's, or a launched dev server's own credential, which only that server's exit or stop revokes and which stays live. So `false` is not proof that the token no longer authenticates, and every case answers the same, so the reply discloses nothing about which credentials exist. The token is never logged or echoed, and an off-schema body is refused in a fixed sentence.

**A credential retired mid-request acts no further.** The middleware authenticates a request before its handler reads the body, which takes as long as the client chooses. So every authenticated route that reads a body — the session, dev-server and panel-data routes, pairing (`pair.start`), telemetry ingest, rotation and release, which include every state-changing route — asks `AuthService.requireLiveCredential` again once the body has arrived, with no `await` between that check and the action it guards. The check and every retirement are synchronous, so none can slip between them. A request whose credential a rotation, release, revocation or expiry retired meanwhile is refused `401` (`unknown-credential` / `expired-credential`) and does nothing: no credential or pairing code is minted, no batch ingested, no panel data read, and nothing rotated, released or changed. A check that cannot reach a verdict fails closed with `500`. The check guards initiation, and that is its residual: work it admitted finishes within the service's own bounds, not the client's — ingest's attribution and storage of a batch the credential was live to deliver, or a dev-server launch that mints its child's credential on the way — so a retirement that lands then races only that processing. `GET` routes read no body, so the middleware's check is their fence. Socket frames are not re-checked; a rotation, release or revocation closes the retired credential's sockets with 4401.

`apps/local-service/src/server/auth.test.ts` and `apps/local-service/test/integration/auth.test.ts` pin these rules: unauthenticated and web-origin requests are rejected; a pairing code works once and fails on reuse and after expiry; a DevTools credential cannot create a session or act on a session bound to another tab, and reads nothing — from no origin or with a forged extension `Origin`, after any hello — without the read proof issued with it at pairing; a server-agent credential cannot ingest for another project or call session routes; an editor credential cannot act outside its announced workspace, including through a symlink inside it; only the editor credential may rotate, purge, or request or release a server-agent credential; rotation through `POST /credentials/rotate` invalidates every existing credential and socket and leaves no journal behind; a release revokes its dev-server credential and closes that credential's socket at once, answers `released: false` for one a rotation already removed and revokes nothing for any other token, and refuses a malformed body without echoing the token; and a credential request, purge, rotation, pairing request, release or ingest batch whose body is held back while a rotation or release retires its credential is refused `401` and has no effect.

## 8. Session data at rest

Everything the product keeps lives under `$DEBUGGEN_HOME` (default `~/.debuggen`), outside every checkout. Treat it as being as sensitive as the projects you debug: it holds diffs and backups of your source.

| Path                                                              | Contents                                                                                                                                                                                                                                                                                         |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `sessions.sqlite` (WAL mode, with its `-wal` and `-shm` sidecars) | sessions and their questions, progress, plans, the modification journal with unified diffs, captures with redacted telemetry, panels, analyses, follow-ups, tab bindings, credential hashes, pairing-code hashes and per-session request-key secrets (`apps/local-service/src/store/schema.sql`) |
| `backups/<sessionId>/<originalHash>`                              | the original bytes of every file the product instrumented                                                                                                                                                                                                                                        |
| `index/`                                                          | the code-index cache for projects you have opened                                                                                                                                                                                                                                                |
| `auth.json`                                                       | the editor credential, in plaintext                                                                                                                                                                                                                                                              |
| `auth.json.pending`                                               | present only while the editor credential is being replaced (first start or rotation, [section 7.7](#77-rotation-and-revocation)): the journal holding the new editor credential in plaintext, mode `0600`, removed once `auth.json` is published                                                 |

**Permissions.** The directory tree is created `0700` and every file `0600`. `packages/shared/src/node/safe-fs.ts` creates files with an exclusive, no-follow open after verifying that each parent is a real directory owned by the current user with mode `0700`, and refuses otherwise — including an existing directory that already grants group or other access, which it reports rather than repairs. A symlink planted at a path it is asked to create yields an error instead of being followed (`safe-fs.test.ts`).

**Retention.** `apps/local-service/src/store/retention.ts` runs on service start and on the VS Code command `debuggen.purgeSessions`, which calls `POST /sessions/purge` with the editor credential. Concurrent purge requests share one running sweep, which never touches a session inside the retention window; each reply carries counts, the cutoff, a problem count and the ids of aged sessions kept for a conflict (at most 100, plus their total), and never a path:

- sessions whose last activity is older than `DEBUGGEN_RETENTION_DAYS` (default 30) are deleted together with their telemetry, panels, analyses, request-key secret and backup directory;
- backup files no journal record references are deleted once they are 7 days old (the gap covers a crash between backup and journal);
- index caches for projects not opened within the retention window are deleted;
- **conflict backups are exempt until the conflict is resolved**, because they may be the only copy of the original file.

Every deletion re-checks that its target lies inside `$DEBUGGEN_HOME` and refuses to follow a symlink.

**Deleting everything.** End every active session so its instrumentation is restored, resolve any reported conflict, then run `debuggen.purgeSessions` or remove `$DEBUGGEN_HOME` entirely. Do not remove it while a session still holds applied modifications or an unresolved conflict: the backups are the record of what the files contained.

## 9. Extension permissions

### 9.1 Chrome extension

Declared in `apps/chrome-extension/manifest.config.ts` and asserted field by field against the built manifest by `apps/chrome-extension/test/manifest.test.ts`:

| Permission or declaration                                                     | Why it is needed                                                                                                                                                                            |
| ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `storage`                                                                     | the paired `devtools` credential in `chrome.storage.local`; the tab-to-session bindings in `chrome.storage.session`                                                                         |
| `alarms`                                                                      | a keepalive for the service worker's WebSocket to the service, because Manifest V3 suspends an idle service worker after roughly 30 seconds                                                 |
| `tabs`                                                                        | observing committed navigations to re-arm the agent or unbind the tab, and the reload the developer consents to when a page loaded before the extension                                     |
| `host_permissions`: `http://localhost/*`, `http://127.0.0.1/*`                | the local app origins only — no `https:` origins, no wildcard hosts — which is also what permits a MAIN-world content script on them                                                        |
| `devtools_page`                                                               | contributes the "Debug Generator" panel; element selection evaluates a descriptor of `$0` in the inspected page through `chrome.devtools.inspectedWindow.eval`, only while DevTools is open |
| content script `agent.iife.js`, `world: "MAIN"`, `document_start`             | the telemetry agent; the React DevTools hook must exist before React loads, so it cannot be injected later                                                                                  |
| content script `src/content/bridge.ts`, `world: "ISOLATED"`, `document_start` | the relay between the page agent and the service worker over a private per-document channel: tagged, versioned, size-capped, provenance-pinned frames                                       |
| module `background.service_worker`                                            | the authenticated WebSocket, the tab-to-session registry and the arming of the agent                                                                                                        |

Both content scripts are top-frame only (`all_frames: false`). Not declared: `scripting` (nothing is registered or injected dynamically), `action` or popup, `options_page`, `externally_connectable` (so no web page can message the extension), `cookies`, `webRequest`, `debugger` and any broad host pattern; the manifest authors no `web_accessible_resources` (the build adds one entry for the bundled bridge chunk).

A MAIN-world script shares the page's JavaScript realm, so the agent is constrained accordingly:

- it runs only on the two local app origins;
- it is **dormant until the service worker sends a configuration for a bound tab** — at `document_start` it only installs the React hook, publishes a disabled helper and opens its channel to the bridge; no capture listener, observer, `fetch` patch or fiber subscription exists until then — and it returns to dormant when the configuration is cleared;
- the only global it exposes is `globalThis.__DEBUGGEN__`: the span helper patched functions call, the element descriptor used for `$0`, and a diagnostic copy of its configuration;
- its channel to the bridge is private rather than secret, and carries no token: at `document_start`, before any page script runs, the bridge asks once on `window` and the agent answers with a detached node it never inserts into the document; every later frame, in both directions, is an event on that node and never touches `window` or `postMessage`. A page script that starts later can neither reach the node nor observe, inject or replay a frame. The agent's control path — receiving a frame, delivering it to its handler, parsing an `agent.config` and deciding what to arm or disarm — runs only on built-ins captured when the agent loaded and on null-prototype storage, so such a script can neither obtain a handler that applies a configuration (an all-false one would disarm a live capture) nor change what a delivered configuration asks for; and every outbound frame is serialised without consulting `toJSON` or running a getter, so it cannot rewrite an `agent.ready`, `agent.error` or telemetry batch as the agent sends it (`packages/telemetry/src/browser/transport.ts`, `packages/telemetry/src/browser/agent.ts`, `apps/chrome-extension/src/content/bridge.ts`);
- the bridge still treats every agent frame as untrusted: it bounds each at 512 Ki UTF-16 code units, parses it, requires canonical opaque document, producer, capture and session ids and the closed `agent.error` vocabulary, pins the document and producer named by the first `agent.ready`, refuses a frame that names another or a batch whose `batchSeq` does not strictly increase within its capture, meters telemetry at 2 000 events per second per document with a burst of 10 000 and adds whatever it refuses to the next relayed batch's `droppedCount`, and logs nothing; it takes custody of a frame only once the runtime port has accepted it, and the service worker holds batches that arrive before its socket is open, re-checks every frame with the same guard and tells the panel, in fixed wording with a count, when events were dropped or could not be delivered (`apps/chrome-extension/src/shared/messages.ts`, `apps/chrome-extension/src/background/service-worker.ts`);
- **residual risk:** the channel does not protect against code that ran before the agent — another extension's MAIN-world `document_start` script, an automation tool's init script, a modified browser — which can replace the primitives the agent captures or take the node; nor against a page script that rewrites the built-ins the agent's signal producers use while they attach or record — event listeners, observers, the `fetch`/`XMLHttpRequest` patches, the page's clock and timers — which can keep a signal from attaching or suppress or distort what it records (without changing the configuration the agent applied, and without the agent necessarily noticing), and a synthetic `pagehide` event, which releases element description until the next `pageshow`; nor against the page's own behaviour, since real clicks, renders, requests, errors and calls to `__DEBUGGEN__.span` are recorded faithfully. Page telemetry is therefore evidence of what the page did, never a tamper-proof measurement: the service validates, bounds and redacts every field, and treats a producer-stamped source location as a claim, keeping a patch location only on a function span and only when an in-force record of the session's modification journal adds, in its diff, the exact file, line, column and symbol the patcher wrote there (so a claim naming an instrumented file with an invented position is refused), and computing every other location itself (`apps/local-service/src/telemetry/ingest.ts`, `apps/local-service/src/source/resolve.ts`);
- it is byte-identical to the built `packages/telemetry` bundle: `scripts/copy-agent.mjs` copies `packages/telemetry/dist/browser-agent.iife.js` into the extension, and the build verifies the SHA-256 of the emitted file.

### 9.2 VS Code extension

`apps/vscode-extension` activates on its own view (`onView:debuggen.session`), on `onUri` and on its contributed commands. It reads the open workspace folders to determine the project root, starts the service bundled in the extension when none answers `/health` (unless `debuggen.autoStartService` is off), reads `$DEBUGGEN_HOME/auth.json` to authenticate, and opens files at locations with `window.showTextDocument` along two paths with different checks ([section 6.5](#65-source-open-containment)). A normal open arrives as a WebSocket `source.open` from the service, which has already applied its lexical and filesystem containment: `apps/vscode-extension/src/extension.ts` takes the project root from the session's stored record (its own state, or the service's `GET /sessions/:id`), never from the frame, and `src/source/open-location.ts` re-validates the location's shape and lexical containment, then resolves it with `fs.realpath`, requires a regular file matching the service's pin and verifies the loaded document before revealing the canonical path, without a confirmation prompt; the `debuggen.openSource` command and the view's `openFile` frame pass through the same checks, minus the pin. Only a `vscode://debuggen.debug-generator/open` URI goes through `src/uri-handler.ts`, which adds independent parameter parsing, `fs.realpath` containment against the open workspace folders, a regular-file check and the modal "Open ‹file›:‹line›?" confirmation. It sends the editor credential only to `debuggen.serviceUrl` (default `http://127.0.0.1:43117`), a `machine`-scoped setting that a workspace's own settings cannot override; keep it on loopback. On deactivation it ends the active session so cleanup runs.

## 10. Secrets handling

- **Tracked environment files.** Only `.env.example` and `apps/demo-app/.env.example` are tracked, and both hold placeholders or the throwaway local-container credential of the demo database. `.gitignore` excludes every other `.env*` variant, `*.sqlite*`, build output, logs and captured telemetry other than the curated, redacted fixtures under `packages/telemetry/test/fixtures/`.
- **The provider credential.** `ANTHROPIC_API_KEY` is read from the service's environment by `packages/model-provider/src/factory.ts`. It is never written to the store, never logged and never placed in a prompt; error messages name the variable, never its value.
- **Service credentials.** Stored as hashes only ([section 7.1](#71-three-role-bound-credentials)). `DEBUGGEN_TOKEN`, `DEBUGGEN_INGEST_URL` and `DEBUGGEN_PROJECT_ROOT` are injected into launched processes and are deliberately absent from `.env.example`; a token set by hand is never valid. `scripts/dev-instrumented.mjs` (`pnpm demo:instrumented`) never prints, logs or writes the editor credential it reads, and sends it only to a listener that proves it is the service ([section 7.3](#73-the-two-unauthenticated-operations)). With `--spawn-local` it requests a server-agent lease and hands that token to the dev server it spawns as `DEBUGGEN_TOKEN`, never printing it, and releases it through `POST /credentials/release` once that dev server has exited ([section 7.1](#71-three-role-bound-credentials)). The child receives only an allowlisted environment — the same list the service's launcher uses (platform, toolchain, locale, terminal, proxy, dev-server, database and `NEXT_*` variables, and `DEBUGGEN_LOG_LEVEL`) plus the names passed with `--env`. Variables off the list, such as `ANTHROPIC_API_KEY`, cloud keys and source-control tokens, never reach the project's code; the listed ones pass as they are, and some carry secrets of the project's own (`DATABASE_URL`, `PGPASSWORD`, credentials in a proxy URL, a `NEXT_*` value), as they would for any dev server started from that terminal.
- **The repository gate.** `pnpm check:secrets` (`scripts/check-secrets.mjs`) runs inside `pnpm verify` and in CI. It reads every file `git ls-files` lists and fails on a tracked environment file other than the two examples, provider-key prefixes, JWT-shaped strings, private-key headers, values of 32 or more characters above 4.0 bits per character bound to key-like names, and connection strings with embedded credentials. Its only exemptions are the two development placeholders in `scripts/check-secrets.allowlist.json`, each matched by exact value and permitted path. It never reads the git directory and fails closed when it cannot inspect the repository.
- **CI.** The workflow clones fresh and never archives or caches the git directory.
- **Logs.** The service logs locally through pino to its own standard output, at `DEBUGGEN_LOG_LEVEL`. Records carry counts, identifiers, rule ids and redacted attributes — never raw event payloads, credentials, request-key secrets or file contents — and pass through the two redaction layers of `apps/local-service/src/logging.ts`.

## 11. Reporting a vulnerability

Please report a suspected vulnerability privately, and do not describe it in a public issue, discussion or pull request.

1. **Report privately** through a GitHub private security advisory on [github.com/ConnerArdman/debugging-generator](https://github.com/ConnerArdman/debugging-generator), the repository the root `package.json` `repository` field names: **Security → Report a vulnerability**. GitHub shows that form only when private vulnerability reporting is enabled, which it offers for public repositories only. If the form is unavailable to you, open an issue on that repository that mentions its owner, [@ConnerArdman](https://github.com/ConnerArdman), asks only for a private security contact and contains no detail of the vulnerability — not the component, the impact or the reproduction — then send the report through the channel you are given. Both routes need access to the repository page: while the repository is private, GitHub shows it — and its issues — only to the people it has been shared with, and answers everyone else with "not found". The project publishes no security email address. If you hold a copy of the code but cannot open the repository page, ask the person who gave you the code to relay a request for a private security contact to @ConnerArdman, again with no detail of the vulnerability.
2. **Include** the affected commit or version; the component (VS Code extension, Chrome extension, local service, telemetry agent or preload, instrumentation, model provider, demo application); reproduction steps; the impact you observed or expect; and any logs, with credentials and personal data removed.
3. **Expect** an acknowledgement, normally within five working days, then an assessment and a fix or mitigation plan. Please allow time for a fix before disclosing publicly; you will be credited unless you ask not to be.

**Supported versions.** Debug Generator is a local developer tool distributed from source; fixes land on the default branch, and there are no maintained release branches.
